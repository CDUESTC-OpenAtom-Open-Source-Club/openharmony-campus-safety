# 鸿蒙智安后续专业化迭代计划

> 文档状态：正式测试版开发基线  
> 生效日期：2026-09-08  
> 基线版本：`v0.1.0-beta.2` Demo  
> 团队决策：Demo 开发已经完成；自本计划起进入正式测试版开发，原 A/B/C 代码只读边界不再生效。

## 一、项目定位与总体目标

本阶段不是重新开发应用，而是在现有 `v0.1.0-beta.2` Demo 基础上，逐步形成一个具有真实业务逻辑、角色权限、现场证据和鸿蒙原生特色的校园安全协同应用。

现有项目已经具备事件模拟、事件管理、任务处理、隐患上报、本地持久化、统计、应急联系方式、学生课表和 Android 跨平台运行等能力。后续开发必须以这些成果为基础，原则上只做扩展、修复和必要的适配，不因新功能而推翻已有架构。

本阶段的目标是：

**保留现有 Demo → 修复业务与数据问题 → 加入本地账号和角色权限 → 完善真实事件处置 → 增加可验证的鸿蒙原生能力 → 完成 UI、测试与发布。**

项目定位为“面向校园安全场景的原生移动端协同工具”，而不是覆盖所有校园生活功能的综合平台。

### 1.1 资源约束

目前可用资源为鸿蒙云手机、Android 手机、现有开发电脑以及三人团队。没有自有云服务器，也没有可用于完整鸿蒙分布式测试的多台设备。

因此，本阶段不强制建设云后端、不依赖真实物联网设备、不购买额外硬件、不承诺跨设备实时协同。所有必做功能必须能够在现有设备上完成开发、验证和演示。

鸿蒙原生能力优先选择服务卡片、系统图片选择、图片处理、扫码识别、系统通知等单设备能力。具体接口须与项目当前 SDK 版本兼容，并经过云手机实际验证后才能纳入最终承诺。

## 二、现有 Demo 的保留与演进原则

### 2.1 保留现有核心成果

现有 `EventSimulator`、`EventRepository`、`EventService`、`EventWorkflowService`、ArkData RDB、Preferences、事件与任务模型、主要页面及测试体系继续保留。新功能优先复用已有接口，不复制第二套事件系统，也不重新实现已经稳定的业务逻辑。

原有“模拟事件 → 确认 → 派单 → 处理 → 完成”链路继续作为开发回归和比赛演示能力。后续增加审核等状态后，可以提供新版完整流程演示，同时保留必要的旧版兼容测试，避免原有测试成果失效。

### 2.2 建立演示模式与日常模式

建议在现有模拟器基础上增加明确的演示模式，而不是删除模拟器。

演示模式使用独立的数据空间，可以生成测试事件、切换演示角色、快速构造不同状态，并一键重置演示数据。日常模式则保留真实用户填写的事件、图片和处理记录，不自动生成模拟数据，也不允许“重置演示”误删日常数据。

两种模式共用同一套业务服务和页面组件，区别只在数据源、账号来源与演示工具入口。这样既能保留 Demo 的价值，又能保证正式使用时不会出现虚假的安全事件。

演示模式必须明确标识“演示数据”，不能把模拟事件、模拟通知或模拟设备状态展示成真实校园安全信息。

### 2.3 建立稳定基线

在开始下一阶段前，为当前可运行版本建立明确的 Git 标签或基线分支，保存构建记录、测试报告和演示流程。后续每个阶段独立开发、合并和回归。

原有数据库不能简单删除重建。涉及字段和表结构变化时，应采用版本化迁移，确保已有事件、任务和设置能够继续读取。

## 三、第一阶段：修复数据与业务基础

这一阶段优先级最高，因为后续账号、证据和审核都依赖可靠的数据层。

### 3.1 修复任务结果持久化

当前 `Task` 模型包含处理结果 `result` 和完成时间 `completedTime`，但 RDB 任务表及其读写映射没有完整保存这两个字段。应补齐数据库字段、写入与读取逻辑，并增加数据库版本迁移。

验收时必须验证：填写处理结果、完成任务、关闭应用、重新启动后，处理结果和完成时间仍然存在；旧版本数据迁移后不丢失。

### 3.2 完善状态机与审核流程

现有事件模型已经预留“待审核”，但任务完成后会直接将事件置为“已完成”。下一阶段应在现有状态机上补齐审核，而不是重新设计整套流程。

建议主流程为：

上报待确认 → 管理员确认 → 派单待处理 → 巡检人员处理中 → 提交处理结果 → 待管理员审核 → 审核通过 → 已完成。

审核不通过时，返回待处理或处理中，并记录驳回原因。重复确认、重复派单、重复完成、已关闭事件回退等情况必须受到业务规则限制。

普通用户提交的优先级应视为建议等级，管理员确认时可以调整最终处置优先级，避免任何用户都能直接将普通事件标记为最高级别并影响管理流程。

### 3.3 完善数据一致性

现有 Repository 使用同步缓存和异步持久化写穿。后续应区分“操作已提交到内存”和“持久化成功”，避免数据库写入失败但页面仍提示最终成功。

建议逐步加入明确的操作结果、错误处理、关键业务事务、防重复请求和数据版本检查。事件创建、派单、任务状态变化等关键操作应保证状态一致，不出现任务已完成但事件未更新、重复生成任务或处理结果丢失。

同时统一时间格式、ID 生成规则和数据校验，避免继续依赖任务数量生成可能重复的任务编号。

### 3.4 阶段验收

原有 Demo 仍可运行；旧数据迁移成功；任务结果和完成时间可持久化；审核与返工链路通过；原有测试不退化，并新增迁移、异常、重复操作和状态机测试。

## 四、第二阶段：本地账号与角色权限

### 4.1 目标

在不依赖云服务器的条件下，实现可实际使用的本地多角色账号系统，使不同角色拥有不同工作台和业务权限。

现有模型已经包含学生、教师、安保人员和管理员角色，可在此基础上扩展，不需要重新建立一套完全不同的用户体系。

### 4.2 账号方案

第一版采用本地账号体系，支持登录、退出、切换账号、修改密码和必要的账号管理。演示模式可以预置测试账号，日常模式则由管理员创建或授权本地账号。

账号记录与个人偏好分离，使用稳定的 `userId` 关联事件和任务，而不是仅用姓名作为身份。密码不得明文保存，应采用成熟的密码哈希方案和随机盐；敏感配置使用适当的系统安全存储能力。

需要明确：本地账号可以实现应用内角色隔离，但不能等同于可信校园身份认证，也无法替代服务端对恶意客户端的授权校验。项目文档应准确说明这一边界。

### 4.3 角色权限

普通用户（学生、教师）可以上报隐患、查看自己的上报记录、查看处理进度和反馈结果，不能确认事件、派单、修改他人任务或访问管理数据。

巡检人员可以查看分配给自己的任务、接单、填写处理结果、提交处理证据和申请完成，不能自行审批自己的处置结果。

管理员可以查看管理范围内事件、确认与调整优先级、指派处理人员、审核处置、驳回返工、管理本地账号以及查看管理统计。

初期不必将学生和教师做成两套独立界面，但应保留角色扩展能力。

### 4.4 权限实现原则

权限不能只依赖页面按钮隐藏。应建立统一的权限检查入口，由业务服务在执行关键操作前验证当前身份与操作权限。

例如，普通用户不能通过直接调用确认接口完成管理员操作；巡检人员不能修改未分配给自己的任务；管理员也不能仅凭页面上的角色选择获得权限。

演示模式的角色切换应与日常模式隔离，不能成为绕过日常权限的入口。退出或切换账号时，应清理当前会话状态和不应继续显示的个人缓存，但不能误删其他账号的持久化数据。

### 4.5 阶段验收

使用普通用户、巡检人员和管理员三个测试账号，可以在同一设备上完成完整协同流程。不同账号看到的数据和可执行操作不同，越权调用被拒绝，退出重登后数据仍然存在。

## 五、第三阶段：真实业务功能深化

这一阶段不追求增加大量新模块，而是将已有安全事件流程做得更接近实际使用。

### 5.1 真实现场图片证据

当前上报页的照片功能仍是模拟状态，应优先替换为真实图片选择与本地保存。

第一版实现系统相册选择、图片预览、移除、压缩、保存和事件关联。图片保存到应用持久化目录，数据库只保存附件元数据和受控路径，不依赖可能被清理的临时缓存目录。

之后增加巡检人员处理前后照片、管理员查看证据、附件删除与异常处理。图片数量、大小和格式设置合理限制，避免大图导致存储膨胀或页面卡顿。

鸿蒙端优先采用 Media Library Kit 的系统图片选择能力。官方已建议使用 `photoAccessHelper.PhotoViewPicker`，而不是继续采用旧版文件 Picker。相机拍摄作为增强项，需先确认云手机是否支持；不支持时保留相册选择和测试图片导入，不再用“模拟拍摄成功”冒充真实证据。citeturn858791search2

### 5.2 我的上报与处理进度

普通用户增加“我的上报”入口，按待确认、处理中、已完成等状态查看事件。详情页展示事件编号、提交时间、地点、当前状态和处理进度。

管理员审核完成后，普通用户能够看到最终处理说明。必要时允许补充说明或反馈，但不能随意修改已经进入处置流程的原始证据。

### 5.3 真实派单与任务责任

移除固定默认处理人员的业务依赖，管理员从本地巡检人员列表中选择负责人。任务记录真实 `assigneeId`、创建时间、接单时间、处理期限和完成时间。

巡检人员只看到自己的任务，并可按待处理、处理中、待审核和已完成进行筛选。管理员可以查看未分配、超时和待审核任务。

### 5.4 操作历史与审计记录

为事件增加操作历史，记录操作者、操作时间、操作类型、状态变化和必要备注。

例如：某管理员确认事件、某巡检人员接单、提交处理结果、管理员驳回、再次处理、最终审核通过。

这些记录应由业务操作自动生成，而不是靠用户手动填写。它们既能提升专业性，也能为后续统计和问题追溯提供真实数据。

### 5.5 应急求助与安全边界

保留现有应急联系方式和系统拨号、短信能力，但应明确区分真实联系电话与演示号码。未配置有效号码时不应展示可能误导用户的一键求助入口。

正式界面不应声称已经接入学校保卫处或真实应急平台，除非确实获得相应号码和授权。拨号与短信继续交由系统界面处理，不自动发送未经用户确认的求助消息。

### 5.6 阶段验收

普通用户能够真实提交文字与图片；管理员确认并派单；巡检人员提交处理结果和证据；管理员审核或驳回；普通用户查看最终反馈。整个流程在应用重启后保持完整，且所有操作有记录。

## 六、第四阶段：鸿蒙原生特色建设

本阶段的目标不是堆砌 HarmonyOS API，而是让原生能力直接改善校园安全业务。

现有项目已经采用 ArkTS、ArkUI、Stage、Navigation 和 ArkData，并完成 ArkUI-X Android 适配。后续应在此基础上增加鸿蒙端特色，而不是为了跨平台一致性放弃原生能力。

### 6.1 必做候选一：校园安全服务卡片

建议将服务卡片作为第一项重点验证的鸿蒙特色。

普通用户卡片提供“快速上报”和“我的上报”入口；巡检人员卡片展示待办数量与最近任务；管理员卡片展示待确认、待审核和高优先级事件数量。

第一版不必做复杂动态图表，只需保证数据来自真实本地业务数据，点击后能够直达对应页面。卡片不得显示模拟网络连接状态或虚构统计。

Form Kit 支持服务卡片创建、信息展示与点击交互，但具体模板、刷新方式和云手机桌面支持需要按现有 API 20 工程进行验证。官方文档也说明卡片存在独立的开发和调试约束，因此应先完成最小卡片样例，再接入业务数据。citeturn858791search5

### 6.2 必做候选二：原生图片证据

图片证据既是业务功能，也是最自然的原生能力展示。可以围绕系统 Picker、图片处理、应用私有存储和权限最小化形成完整技术链路。

如果服务卡片在云手机环境中存在无法解决的限制，图片证据可以作为稳定的原生特色主线，而不影响业务交付。

### 6.3 增强项：扫码定位隐患

可以为测试场景生成二维码，例如某实验室、配电箱或消防设施。扫描后自动填入地点与设备编号，再进入上报页面。

二维码内容只保存必要的地点或资产标识，不需要真实校园资产系统。应用应校验二维码格式，避免任意字符串直接成为可信资产信息。

优先验证图片识码，再验证相机扫码。官方 Scan Kit 提供从本地图片或字节数据识别二维码的能力，但云手机的具体支持情况仍需实际测试。若相机不可用，可以保留图片识码或手动输入作为替代方案。citeturn858791search1

### 6.4 增强项：本地通知与提醒

可以增加任务分配、待审核、处理期限和状态变化的本地通知。通知点击后进入对应任务或事件。

本地通知只反映当前设备已知的数据，不声称能够向另一台设备实时推送。对于定时提醒，应先验证系统提供的后台代理提醒能力及权限，而不是依赖应用长期在后台运行的普通定时器。官方相关能力从 API 20 开始支持模拟器开发，可作为可行性验证方向。citeturn858791search14

### 6.5 暂不作为必做项的能力

真实分布式软总线、跨设备应用接续、远程相机、物联网自动采集、云端实时推送和独立元服务发布，均不列为本阶段必做。

这些能力可以保留技术预研文档，但只有在设备、系统版本、开发者资质和实际测试条件满足后，才进入开发计划。不能将普通本地角色切换、Android 跨平台运行或 HTTP 数据同步称为已经实现的鸿蒙分布式能力。

## 七、第五阶段：统计与产品可信度优化

现有统计功能继续保留，但应逐步从展示型指标转向可解释的业务指标。

建议优先增加事件总数、待确认数、处理中数、待审核数、已完成数、平均响应时间、平均处理时长、按期完成率和超时未处理数。所有指标必须由真实事件和任务数据计算，空数据时明确显示暂无数据或不适用。

当前首页健康度采用自定义扣分规则，并设置了最低分数。后续可以保留为“自定义风险指数”，但应说明计算规则，不将其直接描述为客观的校园安全水平。

同时修复固定日期、固定星期、固定学期周数以及与真实能力不一致的文案。比如尚未接入物联网时，不应显示“正在连接校园物联网感知网格”这样的真实连接提示。

学生课表作为已有功能保留，但后续不再优先扩展成绩、选课、校园商城等与安全主线关联较弱的功能。

## 八、第六阶段：UI/UX 统一优化

UI 放在主要业务稳定之后集中处理，但不意味着前面完全不管可用性。新增功能必须先保证页面可操作、状态清晰、错误反馈准确，最后再统一视觉。

最终 UI 应围绕角色化工作台重新组织信息。普通用户首页突出快速上报、我的上报和应急入口；巡检人员首页突出待办、处理中和超时任务；管理员首页突出待确认、待审核、派单和统计。

视觉层面统一颜色体系、字体层级、间距、卡片、按钮、图标、状态标签和空状态。减少过小字体、过密卡片和装饰性信息，让重要操作具有明确的视觉优先级。

同时完成深色模式、不同屏幕尺寸、横竖屏适配、输入法遮挡、长文本、无障碍标签和触控区域检查。现有 ArkUI-X Android 版本继续保留，对鸿蒙专属能力采用平台适配或合理降级，不要求两端所有功能完全一致。

## 九、架构演进与模块边界

### 9.1 总体架构

继续采用现有分层思想，在必要位置增加账号、权限、附件和原生能力适配。

建议目标结构为：

ArkUI 页面 / 服务卡片  
↓  
业务服务与权限检查  
↓  
现有事件工作流 + 账号服务 + 附件服务  
↓  
Repository / 本地数据源 / 平台能力适配  
↓  
ArkData RDB + Preferences + 应用私有文件

未来如果获得可信后端服务，可以在 Repository 或数据源层增加远程实现，而不需要重新编写主要页面和业务模型。但当前不提前建设复杂同步框架，也不为了尚不存在的服务器引入大量抽象。

### 9.2 统一协作与代码责任

Demo 阶段采用的 A/B/C 固定模块边界自 2026 年 9 月 8 日起停止生效。正式测试版开发以里程碑、功能契约、代码评审和测试责任组织协作，不再以历史成员分工限制可修改文件。

任何成员均可在任务需要时修改模型、Service、Repository、页面、组件、配置和测试，但必须先评估跨模块影响，保持现有架构连续性，并为变更补充相应测试、迁移与文档。涉及公共模型、数据库结构、状态机、权限入口和导航契约的改动，应在合并前完成团队评审。

历史文档中的 A/B/C 归属仅用于理解 Demo 阶段背景，不再构成当前开发的只读边界或验收规则。当前统一原则为：围绕同一业务链路协作，改动范围清晰，接口变更可追踪，责任落实到具体任务和评审人。

### 9.3 AI Coding 使用原则

允许使用 AI Coding 提升实现效率，但每项功能必须经过人工确认需求、接口和验收标准。AI 不得擅自扩大范围或重构已有稳定模块；跨模块修改必须说明影响并经过人工审查。

每次提交应保持改动范围清晰，提交身份遵循团队既有约定。重要功能需要有相应测试和实际运行验证，不能以 AI 生成代码或编译成功代替功能完成。

## 十一、最终验收标准

最终版本至少应完成以下一条真实业务链路：

普通用户登录 → 上报隐患并添加真实图片 → 管理员确认与派单 → 巡检人员接单并提交处理结果 → 管理员审核或驳回 → 事件完成 → 普通用户查看反馈 → 管理员查看统计与操作历史。

同时保留原有模拟器和演示模式，能够快速构造测试事件、展示不同状态，并在不破坏日常数据的前提下重置演示环境。

工程层面要求旧数据可迁移、应用重启不丢失关键业务数据、越权操作被拒绝、重复操作不产生错误状态、图片附件能够正常读取、异常情况有明确反馈，且原有业务测试持续通过。

鸿蒙方面至少完成一项与安全业务紧密结合的原生特色，并在现有鸿蒙云手机上实际验证。Android 版本保留已有可用能力，鸿蒙专属功能允许合理降级。

最终交付包括可安装应用、源代码、构建说明、测试报告、功能演示流程、已实现能力清单和已知限制说明。没有实现的云端协同、物联网或分布式能力应明确列为未来方向，不出现在已完成成果中。

## 十二、优先级与范围控制

本阶段必须完成的是：现有 Demo 保留、数据修复、本地账号权限、真实派单与审核、图片证据、完整操作历史，以及至少一项可验证的鸿蒙原生特色。

扫码、通知、更多统计维度和进一步的 UI 动效属于增强项，根据进度选择。真实云后端、校园统一身份认证、分布式软总线、物联网硬件接入和大型 AI 模型均不作为本阶段交付条件。

项目最终追求的不是功能数量最多，而是让已有 Demo 逐步具备真实业务价值、明确的权限边界、可靠的数据处理、可验证的原生技术和完整的工程交付。
